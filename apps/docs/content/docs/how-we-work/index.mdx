Platform is a department at Plain Concepts, and this section is how it builds and runs software, written down. We write it down because "agents merge to production with no engineer in the loop" is the kind of claim that should be checkable rather than taken on faith, and because every Platform project is measured against it. If you are here to set up a project rather than to read about one, go straight to [Adopt in your project](/docs/adopt).

Most Platform apps pass through three phases. They are not a project schedule. What separates them is **who is allowed to start a change**, and each phase hands that right to a wider group.

| Phase | Who starts a change | What the phase produces |
|---|---|---|
| **1. Discovery** | Departments, with engineers | The product decision, the integrations it needs, and the constraints |
| **2. Foundations** | Engineers, with agents | Working software, and the guardrails that bind everything after it |
| **3. Maintenance mode** | Anyone in the business | Small changes, shipped continuously and measured |

## The four pillars

Four repositories carry all of this. Foundations, agent-harness and project-health are private repositories and agentic-workflows is internal, visible to everyone in the organisation; the npm packages they publish are public. When a page here is not specific enough and you have access, the source is the real reference.

Taken in order they form a chain, which is the clearest way to see why there are four and not one: **Foundations** sets the conventions, **agent-harness** puts them into a repository as something agents can act on, **agentic-workflows** runs the agents against it, and **project-health** measures all three. It checks that the guardrails Foundations defines guard each default branch, that the harness and the workflows are installed and current, and how much of what the agents produce merges without a person. Drop any of the first three and the phase it carries stops working. Drop the fourth and nobody can tell whether it did.

Each one also publishes a site: [platform.plainconcepts.com](https://platform.plainconcepts.com) (this one), [harness.platform.plainconcepts.dev](https://harness.platform.plainconcepts.dev), [workflows.platform.plainconcepts.dev](https://workflows.platform.plainconcepts.dev) and [health.platform.plainconcepts.dev](https://health.platform.plainconcepts.dev).

## What Health measures

[Health](/docs/health) is not a phase 3 report. Each of its four areas judges a different link in the chain above, and the phase that link belongs to.

| Area | The question it answers | What it judges | Where the data comes from |
|---|---|---|---|
| **Engineering** | Do the gates that make autonomy safe guard the default branch, and do they pass? Is the code free of padding comments and runaway tests? | Phase 2, against the [engineering standard](/docs/reference/engineering) in Foundations | The repository's own CI facets, or detection from its workflow files; a daily scan of the default branch's source |
| **Delivery** | How often does it ship, how long does a change take to reach production, and how much is rework? | Phase 3 throughput and stability, in DORA terms | GitHub deployments, releases, commits, and the labels on issues and pull requests |
| **Agentic** | Are agent-harness and agentic-workflows installed and current, and how much agent work merges without a person? | Adoption of the second and third pillars | Files on the default branch, versions on npm, merged bot pull requests and the merge gate's verdicts, agent run artifacts |
| **Roadmap** | Who had each issue at each moment, and what is waiting on a person? | The phase 3 pipeline, issue by issue | Issue timelines, the labels the workflows write, and the pull requests that close them |

One rule runs through all four: **a missing metric is a fact about the data, not a gap to fill with a plausible number.** Two DORA metrics are refused rather than estimated, a practice Health could only detect is marked as inferred, and a partial total says how much of it was measured.

## Phase 2 exists to make phase 3 safe

The claim worth paying attention to is not that agents write code. It is that in phase 3 someone who has never opened the repository can file a request and have it implemented, reviewed and merged with no engineer in the loop.

That is only acceptable because of what phase 2 built. Layering rules that fail the build when crossed. A specification that has to be updated when behaviour changes. A test-quality gate that rejects tests asserting nothing. An audit trail no code path can skip. Each one is a constraint an agent cannot argue its way past, and together they are what buys the autonomy.

So the order is not a preference:

<Callout type="warn" title="You cannot skip phase 2 and arrive at phase 3">
  Pointing agents at a repository with no enforced boundaries does not produce a maintenance mode. It
  produces a fast way to generate incidents. The guardrails are the product of phase 2, not a tax on
  it.
</Callout>

This is the same finding DORA published in 2025: AI amplifies what a team already has, good practices and bad ones alike. See the [2025 State of AI-assisted Software Development](https://dora.dev/dora-report-2025/).

## Outcomes belong to the business, means belong to engineering

Phase 3 works because that line is written down and enforced by the intake itself, not renegotiated for every request.

Anyone can ask for a change to an **outcome**: how a screen behaves, what a workflow does, what the wording says, what a business rule or a formula should compute. Requests about **means** stay with engineering: architecture, infrastructure, deployment, authentication, data models, APIs.

The line is drawn by category rather than by size. A small, clear, well-tested request to change how the app authenticates is still an engineering decision, so triage hands it to a maintainer instead of letting an agent build it.

## The phases overlap

A project is rarely in a single phase. The same app can be in maintenance mode for its screens while a new integration is still being worked out in discovery, and the foundations for that integration get built while everything else keeps shipping. Discovery in particular never really closes: it runs alongside delivery rather than in front of it.

What does not vary is the sequence for any one capability. A capability reaches maintenance mode only after its guardrails exist.
