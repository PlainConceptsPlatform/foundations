This page is the practical door into everything the rest of this section describes. It is written for a Plain Concepts engineer setting up a Platform project. The theme, the harness and the workflows are public npm packages; the workflows assume the Platform GitHub App, the Forge gateway and the runner fleet, and Health reads repositories in the PlainConceptsPlatform organisation.

A Platform product app normally joins the **app family**: it starts from the Kitchen-Sink template, so its sign-in, permissions, audit, feature flags, error contract, API surfaces and web shell are the same code as in every other family app, and stay that way. An app that cannot join keeps its **own design** and follows the conventions on this site by hand; that route is at the end of the page.

<Internal>
  Kitchen-Sink, its `BLUEPRINT.md` and the Project-Health-Platform repository are private.
</Internal>

The order below is not alphabetical. Each step is a prerequisite for the one after it, and together they are [phase 2](/docs/how-we-work/foundations) in miniature: give the app the shared platform code, give agents something to act on, put the agents on repository events, and measure all of it from the first day.

## A new app

<Steps>

<Step>

### Install the skill

In the new, empty repository:

```bash
npx skills add PlainConceptsPlatform/Foundations --skill platform-new-project
```

Then ask your agent: *create a new Platform project*. The skill runs the steps below in order and stops to ask what only you can answer.

Always pass `--skill`. Without it the CLI offers every skill in this repository, including the harness skills vendored under `.agents/`. The skill lands in `.agents/skills/platform-new-project/`, recorded in `skills-lock.json`.

</Step>

<Step>

### Start from the template

The agent creates the project from [Kitchen-Sink](https://github.com/PlainConceptsPlatform/Kitchen-Sink)<Internal inline />. The [`platform-new-project` skill](https://github.com/PlainConceptsPlatform/Foundations/tree/main/skills/platform-new-project) reads Kitchen-Sink's `BLUEPRINT.md` and its platform contract, asks for the domain in one message, takes the owned paths from the template, and builds the app's own code in Kitchen-Sink's shape:

```bash
pipx install copier
copier copy --trust -d app_name=<Name> -d app_slug=<name> --vcs-ref <latest v* tag> https://github.com/PlainConceptsPlatform/Kitchen-Sink.git .
```

Copier writes only the paths the template's `.platform/contract.yml` lists under `owned`, the contract among them, plus `.copier-answers.yml`, which records the template version. The contract is what marks the repository as a family app, and every tool reads it: the harness keeps agents off the owned paths, the workflows sync the template and check conformance, Health compares the app with its template. It also lists what to reuse before building, `docs/platform/` and the `@plainconceptsplatform/ui-components` and `ui-theme` packages, and the skill reads and imports them before writing anything of its own. The theme and the shared components are pinned in the pnpm `platform` catalog.

**Why this is first.** Everything after this step produces code that has to fit the app's platform: the harness generates architecture documents from it, the workflows' agents build on it, and Health compares it with the template. Starting from the template means the first screen already has the shell, the theme, sign-in and permissions, and the first update of the shared code is a `copier update` rather than a migration. What the family shares, and who owns which file, is in [Architecture](/docs/reference/architecture#platform-family).

What the new app sets for its deploy comes with the template. The deploy workflows read the GitHub environments from the repository variables `PRE_ENVIRONMENT` and `PRO_ENVIRONMENT`, which default to `pre` and `pro`, so set them only when the environments are named otherwise. There is no smoke secret to create: the app registers readiness probes (`AddReadinessProbe`), and the deploy's readiness gate is the smoke test. Behind the gateway, set `Platform:TrustedProxies` and `Platform:ForwardLimit` as [below](#taking-a-new-template-version).

</Step>

<Step>

### Install the harness

```bash
npx @plainconceptsplatform/agent-harness@latest
```

Then open OpenCode in the repository and run `/repo-initialize`.

The wizard wires the agent team, the `pc-*` skills, the slash commands, and an OpenSpec workspace, and the bootstrap generates `ARCHITECTURE.md` and `DESIGN.md`. In a family app, `ARCHITECTURE.md` describes the app's own domain and links to the platform documentation the template delivers in `docs/platform/` rather than restating it, and `AGENTS.md` gets a "Reuse before you build" block written from the contract's `reuse`.

**Why before the workflows.** Unattended agents are only as good as what they find in the repository. The harness is what turns our conventions from pages on this site into files an agent reads on every run, so installing it first means the very first automated change already follows the rules. Details and the full command set are on [AI x SDLC](/docs/ai) and on the harness's own site, [harness.platform.plainconcepts.dev](https://harness.platform.plainconcepts.dev).

</Step>

<Step>

### Install the workflows

```bash
npx @plainconceptsplatform/workflows
npx @plainconceptsplatform/workflows add --template quality-gates
npx @plainconceptsplatform/workflows add --template platform-template
npx @plainconceptsplatform/workflows add --template app-ci-dotnet-next
```

The first command installs the router, the workers for the routes you pick, the compile script, and the OpenCode CI config. `quality-gates` installs the engineering gates: the coverage, complexity, duplication and mutation scripts and the facets Health reads. `platform-template` installs the weekly template sync and the conformance guard, both driven by the contract. `app-ci-dotnet-next` is the gates CI, with the `Platform conformance` job. Then:

- Add the secrets: `FORGE_API_KEY` for the Forge gateway, and `BOT_APP_ID` and `BOT_PRIVATE_KEY` for the Platform App, which every write that has to start another workflow is made with.
- Set `VERIFY_COMMANDS` in each worker's `env:` to the repository's own verification command. For a pnpm or full-stack repository that is `pnpm verify`, and it should run what CI blocks on.
- Set the floors in `quality.config.json` from the first CI run, just below what it measured.
- Make the CI's last job hand its verdict to the merge train (`dispatch-merge-train`; the CI templates in the package include it), and set `CI_WORKFLOW_NAME` in the router if your CI is not called `App: CI`.
- Pick a free day for the weekly audit in the router's `AUDIT_CRON`, so it does not run at the same minute as every other repository on the shared fleet.
- Compile with `node scripts/compile-agent-workflows.mjs`, commit the generated locks, and watch one real event go through before you trust it.

The labels are created the first time a workflow applies them. `workflows update` later refreshes every managed file and keeps your `env:` values.

**Why this shape.** From this point the repository maintains itself on events: a label added to an issue triggers refinement or implementation, changes arrive as pull requests, a merge train takes them one at a time, and the merge gate merges what is safe and parks only what is dangerous to merge unseen. The full contract, including the label state machine and the merge gate, is on [Agentic workflows](/docs/ai#agentic-workflows), and the catalog's own documentation is at [workflows.platform.plainconcepts.dev](https://workflows.platform.plainconcepts.dev).

</Step>

<Step>

### Register in Health

The list of measured repositories lives in `projects.json` in the private Project-Health-Platform repository<Internal inline />. Ask the repository for its entry rather than writing it by hand:

```bash
gh workflow run discover.yml --repo PlainConceptsPlatform/Project-Health-Platform -f repo=PlainConceptsPlatform/<repo>
```

It reads the repository and prints a suggested entry, writing nothing. Paste it into `projects.json` in a pull request, and check what it cannot know:

- **`type`**, such as `back-front`, `library` or `static-site`, which decides which engineering practices apply to the project.
- **`status`** and **`environments`**: whether it is in production yet, and which deployment environments count as production and staging.
- **The opt-ins**: `"engineeringExcellence": { "enabled": true }` once CI publishes its facets, and `"roadmap": { "enabled": true }` for the Roadmap tab.
- **Permissions**: the Platform App needs read access to Metadata, Deployments, Contents, Issues and Actions on the repository, plus Pull requests for the roadmap. The collector names anything missing rather than writing empty metrics.

**Why bother on day one.** Health is not only delivery numbers. From the first collection it shows whether the engineering gates are in place, whether the harness and workflows are installed and current, whether a family app still matches its template, and where each issue's time goes, and the trends are only comparable if collection starts before the interesting period, not after. What each area measures, and what it refuses to fake, is in [Measuring with Health](/docs/health).

</Step>

</Steps>

## An app that already exists

Install the onboarding skill in the repository:

```bash
npx skills add PlainConceptsPlatform/Foundations --skill platform-onboard
```

Then ask your agent: *onboard this project*. The skill decides between the two routes below with you, after a preflight that changes nothing.

**Joining the family** is adopt, then converge. The [`platform-onboard` skill](https://github.com/PlainConceptsPlatform/Foundations/tree/main/skills/platform-onboard) runs it as a sequence of pull requests:

1. **Preflight.** A binary scan of what the app already has: harness, workflows, gates, frontend stack, .NET guardrails, and which family capabilities exist in some form.
2. **Adopt.** `copier copy --trust --overwrite -d app_name=<Name> -d app_slug=<name> --vcs-ref <tag> https://github.com/PlainConceptsPlatform/Kitchen-Sink.git .` writes the paths the template's contract lists under `owned`, the contract among them, and nothing else. The app does not compile against them yet, and that is expected.
3. **Converge, one capability at a time.** Sign-in and session, permissions, audit, errors, feature flags, the API surfaces, the web shell: for each one, move the app's code onto the platform code and delete its own version, behind the app's tests. A capability the app cannot move yet gets a dated entry in `.platform/exceptions.yml`.
4. **Quality gates.** `workflows add --template quality-gates` and `--template platform-template`, with the app's floors and baselines kept as its own files.
5. **Template sync.** From then on the template sync opens one pull request per template tag, running the contract's `sync.update`, and the conformance guard checks every pull request.

**An own design app** adopts the conventions incrementally, in the order that gives the most value for the least risk: the theme first (the section below), since importing the tokens is the single change that makes an app look like the rest of the Platform; then shadcn components as you next touch each piece of UI; then the [frontend architecture](/docs/frontend) as you split or add features, with new code following the convention while old code migrates gradually; and the harness and workflows once the repository is somewhere an agent can be trusted to work. `platform-onboard` covers that route too, one domain per OpenSpec change, behind Playwright characterization tests so behaviour is pinned before anything moves.

## Taking a new template version

The template sync opens one pull request per Kitchen-Sink tag, and most tags need nothing from the app beyond reviewing it. A few ask for a setting or a small change in an app file, because the template cannot write app files. The release notes of each tag in [Kitchen-Sink](https://github.com/PlainConceptsPlatform/Kitchen-Sink/releases)<Internal inline /> have a "What apps must do" section; this is what the recent ones ask, for the apps that are in the situation.

<Callout type="warn">
  Set `Platform:TrustedProxies` before merging the pull request that takes v1.2.1. The `Dockerfile` it brings no longer lets ASP.NET Core read the forwarded headers on its own, so an app that has not set it keys its per-address rate limit on the ingress and sees `http` as its scheme.
</Callout>

**Deploy and readiness (v1.2.0).**

- Delete `SMOKE_TOKEN_PRE` and `SMOKE_PATHS` from the `pre` environment; nothing reads them any more. Register `AddReadinessProbe` for the reads they covered: each probe is a one-row read through an Application service, runs without a person or a permission, and cannot write. `/api/v1/ready` answers only ready or not-ready and logs which probe failed, so look in the replica's log.
- Set `PRE_ENVIRONMENT` and `PRO_ENVIRONMENT` if the app's GitHub environments are not `pre` and `pro`. The name is part of the deploy identity's federated credential, so renaming an environment would break it.

**Proxies and sessions (v1.2.1).**

- Set `Platform:TrustedProxies` and `Platform:ForwardLimit` in `appsettings.json`. The platform is the only owner of the forwarded headers, and unset, nothing is trusted. For an internal Container Apps instance behind the shared Application Gateway use `0.0.0.0/0,::/0` with a limit of 2, and leave `Platform:TrustedProxies` empty in `appsettings.Development.json`. An external ingress needs a limit of 1.
- A role change now revokes the person's sessions, using an `rvs` stamp in the token. An app test that expects the old token to keep working after a role change refreshes first. An app that implements or calls `ITokenRevocationStore` adapts to `IsRevokedAsync(…, long? stamp)`. Sessions that exist at the update keep working.
- A retried serializable transaction restores the change tracker, so the audit chain cannot fork. Nothing to do.

**Settings and seams (v1.3.0).**

| If the app | It does |
|---|---|
| Has anonymous SPA pages | Lists them in `Platform:AnonymousPages`, such as `["/review"]`, or `Platform__AnonymousPages__0=/review` |
| Protected its SSO cookies under its own purposes before joining | Sets `Platform:LegacySsoPurposes:State` and `Platform:LegacySsoPurposes:Hint` once; both can go after 90 days |
| Frames sandboxed content from its own origin | Sets `Csp:AllowSameOriginFrames=true` |
| Names a platform audit event differently in its history | Passes `new PlatformAuditActions { … }` as the `auditActions` argument of `AddPlatformInfrastructure` |
| Keeps a section behind a flag and wants it over MCP | Declares the section's tools, which are served to the people the section is on for |
| Tests a stale writer over the InMemory provider | Adds `InMemoryRowVersions.Instance` to the context options |
| Reads a whole collection | Uses `PagedResults.ReadAllAsync` on the server and `allItems` on the web |
| Has its own logo or several tours | Passes `logo` and a list of scoped tours to the shell |
| Lints and tests the web platform folder | Lists the platform `test-support/setup.ts` in Vitest `setupFiles`, imports `platformSteiger` in `steiger.config.ts`, and drops its own Biome and Steiger overrides for that folder |
| Has another web package shipped in the API | Gives it a `build:image` script, which the `Dockerfile` builds, and drops its `Dockerfile` exception |

After a sync, check conformance, and read [How it fits together](/docs/how-it-fits#the-life-of-the-template) for how a change travels.

## Without the template: install the theme

A family app gets the theme from the template. An own design app installs it directly:

<Tabs groupId="package-manager" persist items={["pnpm", "npm", "yarn", "bun"]}>

```bash tab="pnpm"
pnpm add @plainconceptsplatform/ui-theme @plainconceptsplatform/ui-components tailwindcss
```

```bash tab="npm"
npm install @plainconceptsplatform/ui-theme @plainconceptsplatform/ui-components tailwindcss
```

```bash tab="yarn"
yarn add @plainconceptsplatform/ui-theme @plainconceptsplatform/ui-components tailwindcss
```

```bash tab="bun"
bun add @plainconceptsplatform/ui-theme @plainconceptsplatform/ui-components tailwindcss
```

</Tabs>

Then initialize it:

```bash
npx @plainconceptsplatform/ui-theme@latest init
```

This copies `components.json`, adds the theme import to your global stylesheet, and shows you how to wire the Outfit font in your root layout. Both packages are public npm packages; there is no registry configuration and no access token. From here on, `npx shadcn@latest add button card dialog` gives you components that already look like a Platform app, unmodified. The stack and the patterns are on [Frontend](/docs/frontend); the .NET side is on [Backend](/docs/backend).

## What not to do

- Do not edit a path the contract lists under `owned` to get unblocked. Fix it in Kitchen-Sink first, or record a dated exception; the [`platform-upstream` skill](https://github.com/PlainConceptsPlatform/Foundations/tree/main/skills/platform-upstream) walks through both.
- Do not wrap the shadcn components in your own abstractions. That is how proprietary component libraries start, and [principle 2](/docs/principles) exists to prevent them.
- Do not fork the theme. Bump the package version (or take the template version that bumps it) to pick up changes.
- Do not move app-specific components into the foundation. The bar is the same need in more than one app; [Contributing](/docs/contributing) covers it.
- Do not point agents at the repository before the guardrails exist. [Phase 2](/docs/how-we-work/foundations) explains why that order cannot be skipped.
