The frontend is a React and TypeScript single-page app, built by Next.js as a static export, routed by react-router and served by the app's own API. Styling is Tailwind v4 with shadcn/ui components, themed by `@plainconceptsplatform/ui-theme`. Dependency injection uses `inversify-hooks`. The rules, and where the family apps chose differently, are in [Architecture](/docs/reference/architecture#stack); this page explains how to work with them.

The idea behind the foundation: share the **look** and the **conventions**, not a component library. Every app installs the same token package and follows the same structure, so a developer moving between apps already knows where things live. Apps still own their own components and features.

| Concern | Choice |
|---|---|
| Language | TypeScript (strict) |
| Framework | Next.js static export + React, routed by react-router |
| Components | shadcn/ui on Radix |
| Styling | Tailwind CSS v4 |
| Theme | `@plainconceptsplatform/ui-theme` |
| Icons | Lucide (`lucide-react`); Tabler in family apps |
| Dependency injection | inversify-hooks |
| Internationalization | react-i18next + i18next |
| Data fetching | TanStack Query |
| Forms | react-hook-form + zod; family apps validate on the API |
| Lint and format | Biome, Steiger for FSD boundaries |
| Markdown lint | markdownlint-cli2 |
| Tests | Vitest + Playwright |

## Architecture

Next.js is the build shell, not the router. `next build` with `output: "export"` produces static files, the root layout loads the fonts and the theme script, and one page mounts the SPA, where react-router decides every route. The API serves the export, so the browser talks to one origin: no CORS, one content security policy, and a session cookie that never leaves the API's host.

The code follows Feature-Sliced Design with the canonical layer names:

```text
apps/web/
  app/          Next.js: root layout + the one page that mounts the SPA
  pages/.gitkeep  empty, so Next does not read src/pages as its Pages Router
  src/
    app/        composition root, providers, router
    pages/      one slice per route, e.g. pages/claims/ui/ClaimsPage.tsx
    widgets/    self-contained UI blocks, e.g. the app shell (earn it)
    features/   user interactions and use-cases (earn it)
    entities/   business models and their api/ui (earn it)
    shared/     ui (shadcn), lib, api, i18n, and platform/ in family apps
```

Two rules carry most of the value. First, **dependencies point one way**: a layer may import from layers below it, never above, and siblings do not import each other. A `feature` can use an `entity` and `shared`, but an `entity` never reaches up into a `feature`. This is what keeps slices easy to move or delete. Second, **each slice has one public entry** (`index.ts`); import a slice through that, never by reaching into its files. Steiger checks both in CI, so a violation fails the build rather than waiting for review.

Start a new app with only `app`, `pages`, and `shared`. Add the other layers when a real need appears, not before. In a family app, `shared/platform/` is the web code the template delivers (shell, theme provider, auth, flags); treat it as read-only and change it upstream. The shell takes the app's own `logo` and a list of tours, each scoped to a path prefix, `allItems` reads a whole HAL collection, and the folder's test helpers, its nested Biome file and its `platformSteiger` override come with it, so the app carries no setting for it. Full layer rules are in [Architecture](/docs/reference/architecture#reference-app-structure-fsd-on-a-nextjs-static-export).

## Theming

Tokens flow through three layers. Primitive values (the raw brand palette) feed **semantic tokens** (`--primary`, `--background`, `--border`, `--radius`), which are exposed as Tailwind utilities. You work with the semantic layer:

```tsx
// Good: semantic tokens adapt to light/dark and to theme updates
<div className="rounded-lg border bg-card p-4 text-card-foreground">
  <button className="bg-primary text-primary-foreground">Save</button>
</div>

// Avoid: hardcoded values drift from the theme and break dark mode
<div style={{ background: "#fff", color: "#0d0e0f" }} />
```

Dark mode is a class on `<html>` (`class="dark"`); the semantic tokens already carry the dark values. A future brand variant swaps the primitive palette without touching component code, which is why the primitive and semantic layers are kept separate. To roll out a theme change across every app, edit the tokens, bump the package version, and let apps update the dependency. See the live values on [Tokens](/docs/tokens) and the rules in [Design guidelines](/docs/reference/design).

## Dependency injection

Frontend apps use `inversify-hooks` so that use-cases and API clients sit behind interfaces and can be swapped in tests. Depend on an interface, register the implementation once in a composition root under `app/`, and resolve it where you need it:

```ts
// contract lives in shared/api/contracts (or with the entity)
export interface IUserContract {
  getById(id: string): Promise<User>;
}

// composition root under src/app/providers: built once, at module load
container.addSingleton<IUserContract>(HttpUserContract, cid.IUserContract);

// in a component
const [users] = useInject<IUserContract>(cid.IUserContract);
```

Components resolve the contract through `useInject`, so a test registers a fake instead. Pass the `cid` id as the second argument: the default id comes from the class name, which a minifier rewrites. Decorators are optional, and the family apps use none. The exact hook API is in the [inversify-hooks](https://github.com/CKGrafico/inversify-hooks) docs. The rule underneath is simple: depend on abstractions, not concretions.

## Components

Use shadcn/ui components directly. Do not wrap them in your own abstraction "just in case", and do not build a parallel component library. They are themed by the tokens with no extra work. Browse the [Components](/docs/components) catalog for each one with usage code.

App-specific components live in the app, in the slice that owns them. A component moves into the foundation only after the same real need shows up in more than one app. See [Contributing](/docs/contributing) for that bar.

## Data fetching

A static export has no server components, so server data goes through **TanStack Query** and the API contracts. Build every query key from one factory per API area, so an invalidation reaches every list and detail it should and nothing else. A family API answers in HAL-FORMS: render the actions a resource offers from its `_templates` rather than recomputing permissions in the client ([REST](/docs/reference/architecture#rest)).

## Forms

Forms use **react-hook-form** with a **zod** schema for validation, wired through the shadcn `Form` components:

```tsx
const schema = z.object({ email: z.string().email() });
const form = useForm({ resolver: zodResolver(schema) });
```

Validate on the client where it helps the person, and show errors inline. The API is the validator that counts: family apps keep form state in the component and show the field errors the API returns with its 422. Always design the empty, loading, success, and error states, not just the happy path.

## Internationalization

Every user-facing string goes through **react-i18next**. This is mandatory, and the rule is absolute: **zero magic strings**. That includes the ones easy to forget, such as `aria-label` on an icon-only button, placeholder text, empty-state copy, validation messages, and date format patterns.

```tsx
const { t } = useTranslation();

// Good
<Button aria-label={t("invoice.actions.delete")}>
  <Trash2 />
</Button>

// Avoid: invisible to translators, and impossible to audit
<Button aria-label="Delete invoice">
  <Trash2 />
</Button>
```

Two consequences worth planning for. Text expands, often by 30% or more, so verify layouts with a longer language rather than only English. And date and number formatting must use the same locale as the active language, which means passing the matching `date-fns` locale rather than relying on the browser default. For right-to-left languages, wrap the app in the `DirectionProvider` from the [Direction](/docs/components/direction) component.

## Testing

Follow the testing trophy, not the pyramid. Vitest with Testing Library covers component and unit tests, colocated as `*.test.tsx` next to the code, and component tests are the main layer: render the slice with its providers and assert what a user sees and can do, through its public API and not its internals, so tests survive refactors. Write plain unit tests only for pure logic with real branches. Do not assert constants, configured defaults or markup attributes. Playwright covers a few end-to-end flows. Anything with real logic ships tests; pure presentational wrappers do not need them.

## Linting and formatting (Biome)

Biome is the single tool for linting and formatting. Each app has a `biome.json` in its own package directory (`apps/web/biome.json`), scoped to the frontend code only. This keeps lint fast — it never scans `.NET`, workflow definitions, or infrastructure files — and it avoids the memory spikes that killed agent workers on shared 8 GB runners.

### Rules every app follows

- **Scope lint to the web package.** Root `package.json` runs `pnpm -r lint`, which delegates to each package's own `lint` script. Never run `biome check .` at the monorepo root: it scans everything and finds hundreds of pre-existing findings unrelated to your change.
- **Exclude tool-managed directories.** Every `biome.json` excludes `node_modules`, `.next`, `dist`, `out`, `e2e`, `.codegraph`, `.opencode`, and `.agents` so Biome does not lint generated or agent-managed files.
- **`biome check` not `pnpx biome`.** Always use the project's installed Biome via `pnpm exec biome` or the `lint` script. `pnpx` downloads a fresh copy and wastes time and memory.
- **Scoped verification for agents.** When an agent fixes a lint failure, it should verify only the changed files: `pnpm exec biome check <changed-file>` — never the whole repository. Full-repo scans surface pre-existing findings and can exhaust runner memory.
- **Pre-commit hook auto-formats.** Every repo has a husky `pre-commit` hook that runs `biome check --write` on staged `.ts`, `.tsx`, `.js`, `.jsx`, and `.json` files before the commit is created. This means no commit — human or agent — can introduce a formatting error. The hook re-stages the formatted files automatically.

### Formatting conventions

| Setting | Value |
|---|---|
| Indent | 2 spaces |
| Line width | 100 (Foundations) / 120 (consumer apps) |
| Quotes | Double (Foundations) / Single (consumer apps) |
| Semicolons | Always |
| Trailing commas | All |
| Import sorting | Enabled (`organizeImports: on`) |

Consumer apps may override line width and quote style to match their existing codebase, but the structure (scoped biome.json, excludes, scoped lint script) must match.

## Linting Markdown

Biome does not touch `.md` files, and `AGENTS.md`, `ARCHITECTURE.md`, ADRs, and OpenSpec specs are read mostly by agents, not people. `markdownlint-cli2` enforces one rule against them: no hard-wrapped prose. Keep each paragraph on a single physical line and let your editor soft-wrap it — a hard-wrapped `\n` is ambiguous between a real paragraph break and a column limit, and that ambiguity gets expensive once the file passes through a chunker, an embedding step, a diff, or an agent doing line-based edits.

### Rules every app follows

- **Every built-in rule is off, `MD013` included.** The one rule enabled is the custom `no-hard-wrapped-prose`, in `.markdownlint-rules.cjs`. An opt-in ruleset means a markdownlint release that adds a rule can never turn your build red on the next dependency bump.
- **One config at the repo root**, `.markdownlint-cli2.jsonc`, not scoped per package like Biome: it has to reach `AGENTS.md` and `openspec/` wherever they live, not just the frontend package.
- **CI has to call `lint:md` on its own.** Root `lint` is `pnpm -r lint`, which delegates to each package's `lint` script, and markdown belongs to no package — so a repo that only runs `pnpm lint` in CI never lints a single `.md` file. Run `pnpm lint:md` as its own step, or change root `lint` to `pnpm -r lint && pnpm lint:md`.
- **Ignore what you do not own.** Agent- and workflow-managed markdown is regenerated from elsewhere, so a finding in it is noise nobody can act on. Exclude `.agents/`, `.opencode/`, and the files `@plainconceptsplatform/workflows` writes (`.github/workflows/agent-*.md`, `.github/workflows/shared/platform-defaults.md`) — lyceum's config is the worked example.

### Adopting it

```json
{
  "scripts": { "lint:md": "markdownlint-cli2 \"**/*.md\"" },
  "lint-staged": { "*.md": "markdownlint-cli2 --no-globs" },
  "devDependencies": { "markdownlint-cli2": "0.23.2" }
}
```

Copy `.markdownlint-rules.cjs` from this repo's root unchanged — the rule is the convention, and it should read the same everywhere. `.markdownlint-cli2.jsonc` is yours: take the shape from here, then add the ignores your repo actually needs, which is where this one and lyceum's legitimately differ.

There is no installer. The harness does not patch a consumer's `package.json` or hooks, so this is a hand edit, once, per repo.

## Common pitfalls

- Hardcoding colors or spacing instead of using tokens. It breaks dark mode and theme updates.
- Wrapping shadcn components or forking the theme in an app.
- Deep-importing across slices instead of going through `index.ts`.
- Reaching from a lower layer up into a higher one.
